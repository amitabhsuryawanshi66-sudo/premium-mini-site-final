# Capability Test Gates

These gates define the bar for serious future mini-sites and presets. Passing normal build checks is not enough. Clean but boring fails.

## Required Gates

1. **Concept-first direction**
   - The site starts from a niche-specific concept, audience, and conversion promise.
   - Palette and copy swaps are not enough.

2. **Niche-specific section architecture**
   - Section order, content types, and interaction surfaces fit the business.
   - A new niche may require different sections, not the same Obsidian/Velour structure.

3. **Reference-backed component/motion choice**
   - Major new components or signature motion choices cite captured references from approved resources or existing brand patterns.
   - The reference is translated to the niche rather than pasted as-is.

4. **Asset richness**
   - Major visuals are subject-led and support the service promise.
   - Serious presets should use client-provided, generated bespoke, licensed, or high-quality adapted visual strategy. Deterministic artifacts alone are acceptable only when intentionally strong enough for the niche.

5. **Signature interaction/motion**
   - At least one memorable, purposeful motion or interaction moment exists when the brief calls for a premium, motion-aware result.
   - Reduced-motion behavior must remain safe and polished.

6. **Conversion clarity**
   - The primary action is clear, reachable, and supported by copy and trust cues.
   - WhatsApp or other CTA paths must be tested.

7. **Mobile 390/412**
   - 390px and 412px mobile views must be separately checked for overflow, clipping, touch targets, CTA reachability, and visual balance.

8. **No same-template reskin proof**
   - The builder must explain what changed beyond color, typography, and copy.
   - If the layout, section rhythm, motion, and visual language remain basically identical, the gate fails.

9. **Layout Independence Gate**
   - Serious preset tests must document the baseline route used for comparison, the new route or preset id, section order comparison, DOM/component hierarchy comparison, navigation behavior comparison, scroll behavior comparison, interaction placement comparison, content sequence comparison, and mobile layout behavior comparison.
   - The gate fails if the only changes are color, copy, card styling, visual texture, CTA label, section names, or asset labels.

10. **Visual proof**
   - Desktop, mobile, target preset route, fallback route, and key interaction or section states must have current proof.
   - Screenshots or browser proof must come from the current branch.

11. **Skill/resource usage proof**
    - Reports must name which real installed skill, plugin, browser reference, or MCP resource was used.
    - Reports must include operational mode, command/tool/reference output, exact decision influenced, and visible result or QA proof.

## Mode-Specific Proof

- UI UX Pro Max: `search.py --design-system` output or focused script result.
- Impeccable: repair-pending until preferred install and detector proof are verified.
- Emil Design Engineering: exact rule citation plus visible implementation effect.
- Design Taste Frontend: exact anti-template rejection or design decision.
- 21st.dev Magic MCP: MCP list/tool output and selected resource proof after install.
- 21st.dev and MotionSites: Browser reference capture proof.
- Stop Slop: reference files and before/after copy cleanup after install.

## Freeze Conditions

Freeze or send back for planning if:

- The work is only a same-template reskin.
- Visuals are label-led, generic, or fallback-looking.
- The task claims premium or reel-level quality without reference capture and current visual proof.
- Motion is decorative, broken, inaccessible, or absent despite a motion-led brief.
- The design depends on fake local approximations instead of real installed skills/resources.
- A report claims skill/resource usage without output, citation, reference proof, or visible decision impact.
